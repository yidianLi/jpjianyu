# 代码审查流程（WMS 项目 · V1.0）

> 配套文档：《代码审查标准.md》
> 目标：让每一行进 `main` 的代码都经过至少一次人工审查 + 自动化门禁。

---

## 一、角色与职责

| 角色 | 谁 | 职责 |
|------|----|------|
| **作者（Author）** | 提交 PR 的人 | 自测通过、填 PR 模板、回复审查意见、推动合并 |
| **审查者（Reviewer）** | 非作者的另一名研发 | 按《标准》逐条审查，给出 🔴/🟡/💭 结论 |
| **把关人（Maintainer）** | 项目负责（jianyu） | 仅合并已满足门槛的 PR，处理争议升级 |

**原则**：作者不能自己审自己的 PR；敏感模块（auth / guards / db / 过账）建议双审查。

---

## 二、分支与提交规范

当前仓库只有 `main` 一条分支，所有人直推——这是质量失控的根因。改为：

```
main                # 受保护，仅能通过 PR 合并，禁止直接 push
  └─ feat/xxx       # 功能分支，从 main 切出
  └─ fix/xxx        # 修复分支
  └─ chore/xxx      # 清理/配置
```

- 分支命名：`feat/过账幂等`、`fix/guard白名单漂移`、`chore/加ruff`。
- 提交信息参考现有 git 风格（中文、动词开头、带影响面），如 `fix(auth): 数据库凭证改为环境变量`。
- **`main` 设为受保护分支**：GitHub 开启 "Require a pull request before merging" + "Require approvals: 1" + "Require status checks to pass"。

---

## 三、PR / MR 生命周期

```
1. 作者：从 main 切分支 → 编码 → 本地自测（含 pytest / 手测关键路径）
2. 作者：push → 在 GitHub 开 PR，填 PR 模板（见 .github/pull_request_template.md）
3. 自动化：CI 跑 ruff + pytest + 构建检查，结果回显在 PR
4. 审查者：在 PR 内逐条评论，标记 🔴/🟡/💭
5. 作者：处理所有 🔴 与未关闭的 🟡，推送更新（同一 PR 继续迭代，不新建）
6. 把关人：确认 🔴 清零 + CI 绿 + 至少 1 审批 → 合并（优先 squash，保持 main 线性）
7. 合并后：删除功能分支，CI 跑一次全量冒烟（smoke.py）
```

**SLA（建议）**：审查者在 PR 开后 **1 个工作日内** 给出首轮意见；作者 **2 个工作日内** 处理完 🔴。

---

## 四、作者自检清单（开 PR 前必过）

- [ ] 本地跑通 `ruff check . && ruff format --check .`（Python）与 `eslint .`（JS）
- [ ] 跑通相关 pytest；无测试的新逻辑已补测试
- [ ] 无密钥/内网地址进源码（已走 env / config/.env）
- [ ] 改了接口字段？已同步 `docs/api-*.html` 与前端原型
- [ ] 写操作已接鉴权 + 幂等 + 审计日志
- [ ] 单文件 ≤ 300 行；超限已拆分或显式说明理由
- [ ] 不在原型目录提交截图 / `.rar` / 解析脚本等垃圾

---

## 五、合并门槛（Definition of Done）

合并 `main` 必须**同时满足**：

1. 🔴 阻断项数量 = 0。
2. 未关闭的 🟡 建议项 = 0，或已在 PR 内显式标记为"已知技术债（tech-debt）"并建 issue 跟踪。
3. CI 状态为绿色（lint + format + test 全过）。
4. 至少 1 名审查者审批（敏感模块 2 名）。
5. PR 描述完整（含变更摘要、测试方式、影响面）。

任一不满足，把关人**不得合并**。

## 六、自动化门禁（把标准焊进工具）

不要让审查者去肉眼找格式问题——交给工具。

### 6.1 Python：`ruff.toml`（已建）
- 替掉 flake8/black/isort，一个工具搞定 lint + format。
- 行宽 100，`E/F` 错误类全开，强制 `type hints`。
- pre-commit 中 `ruff check --fix` 自动修，提交前修不掉则拦下。

### 6.2 Node：`eslint` + `prettier`
- `ai-gateway` 加为 devDependency；CI 中 `eslint .`。
- 当前 `dependencies: {}` 保持不变，lint 工具只进 dev。

### 6.3 `.pre-commit-config.yaml`（已建）
- 提交前自动跑 ruff、eslint、检测密钥泄露（`detect-secrets` 或 `gitleaks` 轻量规则）、禁止大文件。
- 装法：`pip install pre-commit && pre-commit install`。

### 6.4 CI：`.github/workflows/ci.yml`（已建）
- 触发：PR 到 main、push 到 main。
- 步骤：checkout → 设 Python/Node → `ruff check .` + `ruff format --check .` → `pytest` → `eslint .` → 构建冒烟 `python smoke.py`。
- 任一失败，PR 状态红，**禁止合并**。

---

## 七、原型 vs 后端的差异化审查

| 维度 | 后端（FastAPI/Node） | 前端原型（HTML/JS） |
|------|----------------------|---------------------|
| 门禁 | ruff + pytest + eslint 必过 | 仅 eslint + 人工 |
| 测试 | 必须有 pytest | 手测关键路径即可 |
| 审查重点 | 安全/SQL/幂等/接口契约 | XSS/接口对齐/误提交垃圾 |
| 合并频率 | 小步 PR | 可整页 PR，但需标注影响页面 |

> 原型是"演示态"，后端是"生产态"。原型代码也进审查，但标准略宽；一旦某原型页面要转正，须补齐后端级门禁。

---

## 八、度量与持续改进

- 每周看一次：PR 平均审查时长、🔴 数量趋势、CI 红率。
- 每月回顾：把反复出现的 🟡 升级为 🔴 或写进门禁（如"内存 token"在上线前必须消除）。
- 标准本身版本化：本文档与《标准》同走 git，重大修改走 PR 评审，文件名带版本（当前 V1.0）。

---

## 九、落地顺序（建议）

1. **本周**：合并本流程文档 + 四份配置（PR 模板 / ruff / pre-commit / CI）。
2. **本周**：开一个 `chore/安全清理` PR，按《标准》第七节把现有 🔴 一次性修掉（凭证、CORS、护栏漂移）。
3. **下周起**：所有新 PR 走本流程；`main` 开启保护。
4. **两周内**：补 pytest 覆盖 auth / guards / 过账三条核心链路。
